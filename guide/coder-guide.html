Base64 인코딩 원리와 실무 한글 깨짐 해결법

1. Base64 인코딩이란 무엇이며 왜 사용하는가?

Base64는 8비트 이진 데이터(Binary Data)를 네트워크 전송 과정에서 유실이나 변형 우려가 없는 64개의 안전한 ASCII 문자셋(A-Z, a-z, 0-9, +, /)으로 변환하는 대표적인 인코딩 기법입니다.

초기의 이메일(SMTP)이나 레거시 네트워크 프로토콜은 텍스트 전송에 최적화되어 있어, 이미지, 압축파일, 바이너리 토큰 등의 이진 데이터를 그대로 전송하면 시스템별 개행 문자 처리나 제어 부호 충돌로 인해 데이터가 심각하게 손상되었습니다. Base64는 모든 데이터를 공통 텍스트 문자로 치환하여 이러한 플랫폼 간 호환성 문제를 근본적으로 해결합니다.

2. 3바이트를 4바이트로 쪼개는 Base64 수학적 변환 원리

Base64의 핵심 원리는 3바이트(24비트) 크기의 데이터 묶음을 6비트씩 4개로 쪼개어 각각을 64진법 인덱스로 매핑하는 것입니다.

  • 비트 팽창: 3바이트 데이터가 4바이트 문자로 늘어나기 때문에, Base64로 인코딩된 데이터의 용량은 원본 대비 약 **33% 증가**합니다.
  • 패딩(Padding): 원본 바이트가 3바이트로 딱 떨어지지 않고 1바이트나 2바이트가 남을 경우, 부족한 빈자리를 비트 0으로 채우고 끝에 등호 기호(= 또는 ==)를 붙여 패딩 처리를 수행합니다.

3. 자바스크립트 환경에서 한글(UTF-8) 깨짐이 발생하는 결정적 원인

웹 프론트엔드 개발 시 가장 흔하게 겪는 실수가 브라우저 내장 함수인 window.btoa()를 한글 문자열에 바로 사용하는 것입니다. btoa()는 엄격하게 라틴 1바이트(ISO-8859-1) 문자셋만 지원하도록 구현되어 있습니다.

UTF-8 환경에서 한글은 글자당 2~3바이트를 차지하므로, 이를 그대로 btoa()에 넣으면 바이트 범위를 초과하여 InvalidCharacterError 예외가 발생하거나 디코딩 시 복원이 불가능한 문자로 깨지게 됩니다. 따라서 문자열을 먼저 URI 컴포넌트 형식으로 바이트 직렬화한 뒤 Base64로 변환해야 합니다.

// 실무 표준: 한글(UTF-8) 깨짐 없는 안전한 Base64 인코딩 함수 function safeBase64Encode(str) { return btoa(encodeURIComponent(str).replace(/%([0-9A-F]{2})/g, (match, p1) => { return String.fromCharCode('0x' + p1); })); } // 안전한 디코딩 함수 function safeBase64Decode(str) { return decodeURIComponent(atob(str).split('').map(c => { return '%' + ('00' + c.charCodeAt(0).toString(16)).slice(-2); }).join('')); }

4. URL 인코딩(Percent Encoding)과의 차이점

Base64가 바이너리를 안전한 텍스트로 압축·포장하는 용도라면, URL 인코딩은 웹 주소(URL) 체계에서 충돌을 일으키는 특수문자(공백, 슬래시, 물음표 등)를 퍼센트 기호(%)와 16진수 조합으로 치환하여 파라미터 유실을 방지하는 통신 규격입니다. 개발 시 데이터의 성격과 전송 환경에 맞춰 올바른 인코딩 방식을 선택해야 합니다.

5. 무료 온라인 변환 도구 활용

복잡한 자바스크립트 변환 코드를 직접 구현하지 않고도 브라우저 환경에서 즉시 텍스트, URL, Base64 데이터를 안전하게 상호 변환할 수 있습니다.
